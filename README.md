# MPDantic

Pedantic about your library, so MPD does not choke on it.

MPDantic is a Volumio 4 plugin that audits and repairs a music library for MPD, one folder at a time or the whole library from its root. It sizes MPD's output buffer to the player's memory, manages `.mpdignore` files with suggestions drawn from what is on the share, checks and repairs CUE sheets, rebases playlists written on other machines to the player's paths and imports them into Volumio's own, and validates the tags the Albums view is built from. The work is done from MPDantic's own pages, served by its core on the player; the heavy work runs in that Rust core, and a thin Node shell carries the plugin's lifecycle and a settings page that says where the pages are.

## Status

0.1.8 is on the releases page as the latest release, the ninth cut and the first marked as a release: every feature below is in, driven on an x86 player with a real MPD and on a Raspberry Pi 5 up to the eighth cut, and it is published for use on more players and more libraries before it goes to the Volumio plugin store. Install it from the release zip through Volumio's plugin manager; the zip carries the core for `arm`, `armv7`, `armv8` and `x64`, `THIRD-PARTY-NOTICES` with every licence the core is built from and the crates under each, `MANIFEST` and its signature inside, and `SHA256SUMS` and its signature beside it, signed with the evo release key whose public half is `keys/release-signing.pub`. Every write the plugin makes is undoable from its Written tab; still, a test cut on a library without a backup is a test cut on a library without a backup. What it finds, say on the issues page with the player report from the System tab: one block that names the player, its memory, Volumio's and MPD's versions, the library's size, the shares by type and nothing else of them, the output buffer with its bounds, and, after "Measure the album query", how large the album list is against that buffer and how long Volumio's backend would take to read it.

## What the install puts on the player

Volumio's plugin manager unpacks the plugin under `/data/plugins/system_controller/mpdantic` and runs its `install.sh` as root, which checks that the core binary for the player's architecture runs, and puts five things outside that folder: the core's systemd unit (`mpdantic.service`, run as the volumio user with three capabilities, `CAP_DAC_OVERRIDE`, `CAP_CHOWN` and `CAP_FOWNER`, so the core can write the library's files whoever owns them: music copied onto the player through Volumio's own network share belongs to nobody, and a USB disk's files to whoever wrote them; each file the core rewrites keeps its owner and mode, a new file takes its folder's owner, and the unit's `ProtectSystem` keeps `/usr`, `/etc` and `/boot` read-only whatever the capability), the data folder `/data/INTERNAL/mpdantic` (the preferences and the undo journal), the sudoers entry `/etc/sudoers.d/volumio-user-mpdantic` (named after Volumio's own `volumio-user` so it sorts after it, validated with `visudo` before it counts), the mount helper at `/usr/local/libexec/mpdantic-mount` (root-owned, mode 755, outside the plugin tree so a volumio process cannot rewrite what sudo runs), and, once the plugin runs, the Avahi service file that announces the pages. The sudoers entry is self-contained and lists every command the plugin runs through sudo: the core's unit started, stopped and restarted; that mount helper for the read-write mount of a share's folder under `/run/mpdantic/mounts` during a write (CIFS and NFS only, as Volumio mounts them; the mount lives in the core's own mount namespace and is released after the write; raw `mount` and `umount` are not granted); `tee` and `rm` on the announcement file alone, for a player whose Avahi folder is not open to the volumio user. The uninstaller takes the unit, the sudoers entry, the mount helper and the announcement back; the data folder stays, since it holds what the user can undo.

## The output buffer

MPD holds each reply to Volumio in a buffer of at most `max_output_buffer_size` and drops the connection past it. Volumio's album view asks MPD for every song with every tag in one reply, so on a large library that reply outgrows the 80 MiB Volumio's template sets and the album list comes up empty. The plugin sizes the buffer to what the player can take, through Volumio's own MPD configuration hook, so the value survives every rewrite of `mpd.conf`: the line is appended after the template's, and MPD takes the later value (0.21.19 or later; the plugin reads the version and appends nothing to an older one). The size is the smallest of three bounds, never below Volumio's 80 MiB and never above 1 GiB: what the backend's heap can hold (the reply is held as one string and parsed, about six times its size while it is read, two such replies at once), what the player's memory can hold beside Volumio, the kiosk browser, MPD and the core, and what the backend reads in two minutes (its MPD client re-reads its whole buffer on every chunk, so the time grows with the square of the reply). The settings page has the switch, on by default, and says the value this player gets and which bound holds it; the status toast says the same.

On the Raspberry Pi family every Volumio image runs a 32-bit userland, where the backend's heap is 1 GiB whatever the memory; with that and the quadratic read, Volumio's 80 MiB is already what the backend can take, so the plugin appends nothing there and says why. On x86 with 4 GB or more the buffer goes to 128 MiB. This is a mitigation for large libraries, not a cure: the cure is a lighter album query in Volumio's backend. A limitation to know: when MPDantic tells MPD to update, Volumio's database handler rebuilds that album list, which takes a while on a large library. Writes land on disk without that update; **Update library** tells MPD once for every folder written since the last press, so ten albums cost one rebuild, not ten. Leaving the pages with folders still waiting asks whether to update now, leave without updating, or stay.

## The pages

The core serves them on a port of the player (6218 unless set on the settings page), from its memory, for any browser on the network: `http://<player>:6218/`. The settings page opens them inside Volumio's own page, where Volumio's own arrow leads back, or in a tab of their own, which carries a Close button; it shows the address, and on the network the pages are announced as "MPDantic on <player>" for anything that lists Bonjour services. The page is the library as MPD sees it, folder by folder from the roots (`NAS`, `USB`, `INTERNAL`), read on request one directory at a time, never the whole library; under the folder in hand, eight tabs: `Ignore`, `CUE sheets`, `Tags`, `Playlists`, `Volumio`, `Written`, `System` and, last as on every page of the family, `About`. The tab open last time opens again, and `?tab=cue` in the address opens one by name. The buttons follow one rule on every tab: the one on the right of a panel's head starts a read-only job over the folder or the library and changes nothing; the ones under a block's text, on the left, open a card or a grid and change nothing either; a green button is the only thing that writes, with a grey Cancel beside it; an amber button is an undo. The About page says what MPDantic is, that it is part of the evo framework, what it is built of with each piece's licence, and how to support it, each with a code to scan.

The pages are open to the network the player is on, as Volumio's own pages are and as Glass's and Outcast's are: anyone who can reach the player can read the library and write to it from the pages, every write undoable. That is by design for a home player on its own network; it is not a boundary to put between the player and people who should not reach it.

The pages come in eleven languages: English, German, Spanish, French, Italian, Japanese, Dutch, Polish, Portuguese, Russian and Chinese. The settings page follows Volumio's language, as every plugin's does. The management pages follow the player's language too: the shell tells the core the language Volumio is set to, at start and whenever it changes, and the core serves the pages with that language's texts built in. Every sentence the core writes (a finding, a repair, a note on the Written tab, an error) is a key with its arguments and is rendered on the page in the language in hand, with that language's plural forms. `?lang=de` in the address opens the pages in a language of its own, for a look; a language Volumio is set to that the pages do not have falls back to English. The player report on the System tab stays in English on purpose: it is pasted into issues read by the maintainers. MPD's own terms stay as MPD writes them in every language: the key names, the file names, the finding codes.

Under the listing, the `.mpdignore` analysis of the folder in hand: a job walks everything under it, one directory at a time, and says what MPD's update would meet there by class (audio, CUE sheets, playlists, images, archives MPD would open and walk inside, video containers its ffmpeg decoder happens to claim, the folders a NAS writes for itself, the sidecar files a desktop leaves) and which `.mpdignore` lines, already in force from the root down, keep what out. It suggests the lines that would keep the junk out, each with its reason, its count and examples; a line for a suffix carries it as written, since MPD matches case for case. The folder's own `.mpdignore` is edited in the field under the analysis: the file as it is, a line typed is added, a line deleted is removed, an empty field removes the file, and the preview says what is added, removed and kept. The audio suffixes come from the running MPD's own decoder list, kept per plugin, so the analysis matches the MPD on the player: what MPD's own audio plugins claim is music, what its ffmpeg decoder alone claims is shown as its own class, with the text, lyrics and subtitle files it opens and probes at every update suggested as lines. A `.mpdignore` line that starts with a hash is a comment to MPD, and a line like `#recycle` is shown as dead with the line that works, `[#]recycle`. The matching is the same `fnmatch` MPD uses. Video in the library is wanted where Glass plays it: a switch on the page says whether video is in use here, following Glass's presence on the player unless set, and with video in use the video containers are counted and never suggested.

The lines are written from the same tab: every suggestion, and every suffix in the tables of what MPD meets, has a tick that puts its line into the list of lines to write, where lines are typed and edited freely, one pattern per line; the list goes into the `.mpdignore` of the folder in hand. The core prepares the file whole and the page shows it, with the lines it would add, the lines already there and the lines it refuses (a line starting with a hash, which MPD would read as a comment, is refused with the line that works), and nothing is written until the one Write button is pressed. The write checks that the file is still what the preview read, writes the file whole and moves it into place, records the file as it was and as it is under `/data/INTERNAL/mpdantic/undo`, and tells MPD to update the folder. On a NAS share, which Volumio mounts read-only, the core mounts the folder in hand read-write for the write, as the volumio user and through the operating system's own `mount`, with the credentials from Volumio's own share configuration passed in a file only root reads and removed right after; the mount lives in the core's own mount namespace, is released right after the write, and Volumio's mounts and MPD's view of the library are never touched. Every write is listed on the Written tab, newest first, with an Undo that puts the file back as it was, byte for byte (or removes a file the write created, or puts back a sheet the write removed), when nothing else has changed it since, and tells MPD to update the folder again.

Beside it, the CUE check of the folder in hand: every sheet under it read the way MPD reads it (the six commands MPD takes, the FILE types it accepts, the index rule it follows) and what MPD makes of it said per sheet: a FILE type that drops its tracks, a FILE not beside the sheet or there in another case or with another suffix, a FILE no decoder claims, a foreign path, an unquoted name, a byte-order mark, a sheet that is not UTF-8, an index MPD cannot use, two sheets naming the same file, a sheet beside its own split tracks. Each is what MPD does with the sheet as it is; the tracks MPD would make are listed with their starts and ends, and an index past the file's length is said.

A sheet with such a finding has a Repair button. The core says which repairs the sheet's text allows and shows the sheet as it would be with them, line by line against the files beside it: the byte-order mark removed, so MPD sees the first line; the text read as a code page of your choice (Windows-1252 unless chosen, or the UTF-16 its mark says) and written as UTF-8; a `FILE` type MPD drops rewritten to one it takes (`MP3` and `AIFF` where the suffix says so, `WAVE` for everything else, as other tools write it); a `FILE` name rewritten to the file that is beside the sheet in another case or with another suffix, or to the file a Windows or absolute path ends in when it is there; an unquoted name with spaces quoted, so MPD takes all of it. Each repair is a tick; the card shows the sheet as it is and as it would be, says what MPD's parser would still find in the text, and nothing is written until Write is pressed. Where two sheets name the same file, or a sheet names one file and the album's tracks are beside it as files too, the card also offers to remove the sheet, never ticked by itself; the undo puts it back. Everything else in the sheet stays as written, byte for byte: the line endings, the comments, the indentation, the lines MPD ignores. An index MPD cannot use, a track without a file and a file no decoder claims are said and left to the hand.

And the tag check of the folder in hand: every audio file under it read for its tags as written (Vorbis comments, ID3v2 and ID3v1, APE, MP4 atoms, the ID3 tag a DSF or DFF file carries at the offset its header names), then MPD's own rules applied to them, read from MPD's source: which names it takes from each format and as what. The report says, per folder, whether the files agree on Album and AlbumArtist, since Volumio groups an album by those and a folder that disagrees shows as several albums; and per file what MPD would miss: a title, artist or album it cannot read, an album artist or a date written under a name MPD does not read ("ALBUM ARTIST" with a space in a FLAC, "YEAR", a TXXX frame), a track or disc number missing or not a number, text that is UTF-8 read as Latin-1, ID3v1 alone, a tag given twice, a placeholder, an embedded cue sheet beside an external one.

The playlist check of the folder in hand: every m3u, m3u8, pls and xspf under it read the way MPD reads it (the m3u and ExtM3U rules, the `[playlist]` section and the `NumberOfEntries` a PLS must have, the XSPF locations), and each entry resolved as MPD's `load` resolves it, joined to the playlist's own folder with the dot segments squashed, or kept as written when it is absolute or has a scheme. The findings: an entry not found where MPD looks, which MPD skips at load without a word; a foreign path (absolute, a Windows drive, backslashes, `file://`), which is nothing on this player; an entry no decoder claims; a byte-order mark, which hides the ExtM3U header; a playlist that is not UTF-8; a PLS without its section or its count, which MPD rejects whole; an `.m3u8` or `.xspf`, which MPD plays and Volumio's browser never sends to it; an empty playlist. A playlist with such a finding has a Repair button: the entries MPD cannot find are looked for under the folder in hand by the longest tail of their path (the foreign root dropped, backslashes turned, `file://` stripped) and written relative to the playlist's folder, which is what `load` resolves and what other players read; the mark removed; the text re-encoded from a code page chosen on the card; a PLS given its section and count; and for an m3u8 or an xspf a `.m3u` written beside it with the same entries, so Volumio plays it. Everything else in the file stays as written. The card shows every entry as it is and as it would be, the ones still not found, and the file whole; one Write, the undo on the Written tab.

The Volumio tab is for Volumio's own lists: its playlists, favourites, radio favourites and web radios as it keeps them (JSON files under its data folder), and the queue. Each item is checked against the library the way a playlist entry is: found when MPD's decoders claim the file (a video container the ffmpeg decoder claims is found, since Glass plays it), not found where its uri points, a foreign path, a stream, another service, no uri, the same uri again; a file cut short is read as far as it goes and says how many items it still has. A list simply messed up is repaired on the write path with the undo: an item whose file is gone is found again by its name and folders or dropped, a uri in twice is kept once, an item without a uri is dropped, a cut file is written back with what could be read. The queue as it plays now is read from the player's own socket and checked; the items whose files are gone can be taken out through Volumio's own queue, as its page would, which is live state with no undo.

A playlist with entries MPD can load has an Import into Volumio button: the playlist written as one of Volumio's own, under its Playlists, as the JSON file Volumio itself writes when a song is added to a playlist from its browser (`/data/playlist/<name>`, one item per entry with the title, artist and album read from the file's tags, the album art as Volumio asks for it, and a stream as a web radio). The name is the file's stem, changed on the card. An entry MPD cannot find, a foreign path or a file no decoder claims is left out and said; the playlist in the library is not touched. The file is shown whole as Volumio would keep it; one Write; Volumio lists it as soon as its Playlists are opened, and the undo on the Written tab removes it, or puts back the one it replaced. Nothing is sent to MPD.

The obvious edits are written from the same tab, for the audio files of the folder in hand: the album artist and the date written under the key MPD reads, beside the key it does not (`ALBUM ARTIST` in a Vorbis comment becomes an `ALBUMARTIST` too, `YEAR` a `DATE`, a `TXXX` frame a `TPE2` or `TDRC`); text that is UTF-8 read as Latin-1 decoded back; a tag given twice kept as its first value; an ID3v2 tag written from the ID3v1 fields; and, where the folder's files disagree on Album, Album artist or Date, the value every file gets, picked from the values the files carry or typed, since those can all be wrong. Under the repairs, the editor: the folder's audio files as a grid, one row per file and one column per field MPD reads (track, title, artist, album artist, album, date; disc, genre, composer and comment on a tick), every cell editable, a column set for every file at once, an empty cell removing the key; Preview shows every file's changes key by key, Write goes through the same path as the repairs, and the undo sets every key back. The card lists every file with its changes, key by key, before and after; one Write; each file is written through lofty, which writes every format it reads, the audio untouched: before the write the core measures the audio between the file's tags, its length and its first and last 64 KiB, and after the write checks that all three are the same; a difference stops the batch and is said, and a file with no audio between its tags is not written at all. DSF and DFF files are read, not written. The journal keeps each file's changes, and the undo sets every key back when nothing else has changed it since. What is left to the hand is said: a missing title, a track number, a placeholder.

Every check of CUE sheets, tags or playlists keeps its findings whole, under the data folder, so the list outlives the page and the player's restart and the check is not run again to see it. Each of the three tabs says under its head what the last check found and offers to work through it, and each code on the report (the five examples are a teaser) opens that view on that code. In the view, with no code chosen, folders are listed fifty at a time; a code chip opens a table of every matching finding, twenty at a time, with a path that opens the folder and a dismiss that stays through later checks, and bulk dismiss for the selection, the page or every open row of the code. A folder opens to its findings and its repair with the same preview and Write as on the tab; a tag repair lists only the files that change unless Show unchanged is ticked. After a write or an undo the folder is checked again on its own and the list follows, and every listed folder can be checked again without walking the library. The list exports as text in the page's language, one finding per line. Only Close or the browser's back leave the view, after a question while a preview is open, and it reopens where it was. A folder row of the listing has a Keep out that puts the folder's name into the `.mpdignore` of the folder in hand through the same preview and write, and the analysis knows the folders a QNAP and a Netatalk share write for themselves.

The files of a folder are named from their tags, or their tags read from the file names, by one pattern such as `{track} {title}`, the direction chosen on the Tags tab under "File names and tags" and in a folder's card of the findings view. The placeholders are the fields of the grid; the text between them is taken as it is. A name from the tags carries the track as at least two digits and is made safe for a share: slashes, colons and the characters Windows refuses become underscores; a file whose tags lack a field named is left and said; two files that would take one name, or a name already taken, refuse the batch whole. A CUE sheet or an m3u, m3u8 or pls playlist in the folder that names a renamed file is rewritten with it in the same batch; the undo gives the names back and the files their lines. Tags from the names are the edits of the grid: each placeholder takes what stands in its place, the track and the disc digits only, a file that does not fit the pattern is left and said, and the write and the undo are the editor's.

## What it will do

| Feature | What |
| --- | --- |
| Output buffer | MPD's `max_output_buffer_size` set from the player's memory, the backend's heap and the time the backend takes to read a reply, never below Volumio's default, written through Volumio's own MPD configuration hook so it survives every rewrite of `mpd.conf` (in). A mitigation for large libraries, not a cure. |
| `.mpdignore` | The ignore files of a folder tree, from the top down, with suggestions for what MPD cannot play: files whose suffix no installed decoder takes, disk images, video, and the folders a NAS writes for itself. Folder art is never suggested. |
| CUE sheets | Sheets checked for files that are not there, encodings MPD does not read, several FILE entries and index timing, and repaired in place (the text repairs are in; an index rewritten by hand is not). |
| Playlists | M3U, M3U8, PLS and XSPF written on another machine rebased to the player's paths, and imported as Volumio's own playlists with the entries MPD can load (both in). |
| Tags | The tags MPD reads (ID3, Vorbis comments, MP4 atoms, APE, WavPack) validated on any mount and edited where the share allows, Album, AlbumArtist, Artist and Date first; a MusicBrainz release lookup (search ladder, then Preview/Write through the same tag path); Organise to move selected albums out of a mix or dump into Artist/Album folders; folder rename from album or album artist tags. |

Every write goes the way the `.mpdignore` lines go: shown whole first, confirmed once, journaled for an undo, and followed by MPD's update of the folder; on a network share through a read-write mount of the folder in hand made for the write and taken down after.

## How it is built

Two parts in one zip, one copy of the core per Volumio architecture (`arm`, `armv7`, `armv8`, `x64`), nothing of the player's own software relied on:

| Part | What | Where it comes from |
| --- | --- | --- |
| The shell (`plugin/`) | The Volumio plugin as the store wants it: the settings page, the install, the core's service, the pages' announcement on the network. | This repository. |
| The core (`bins/mpdantic`) | One daemon in Rust, started by the shell as its own systemd unit: it serves the pages and the API, and does the work on the library. Static, linked against musl. | This repository, cross-built in CI. |

Every release is built by GitHub Actions from a tag: the check, the cross builds, the zip with `MANIFEST` and its Ed25519 signature inside and `SHA256SUMS` with its signature beside, published as a pre-release and promoted by hand once tried. `build.json` in the zip names the commit.

To work on it: `scripts/check.sh` is the workshop pass (format, lints, tests, docs, the shell scripts, the plugin's files and tests, the pages' scripts), `scripts/ship.sh` the cross builds, `scripts/package.sh` the zip. The Rust toolchain is pinned by `rust-toolchain.toml`; Node is needed only for the plugin's checks. The core runs on a workstation too, for the pages against any folder: `mpdantic --run /tmp/mpdantic --music /path/to/music --mpd 127.0.0.1:6600` (without an MPD to ask, the analysis assumes the usual audio suffixes and says so).
